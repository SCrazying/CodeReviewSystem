## 1. 产品概述

### 1.1 背景与问题

研发团队使用 Git(Gitea/GitLab)管理代码,代码审查依赖人工 + 零散工具,存在以下痛点:

1. **审查成本高**:MR 人工 review 耗时长,常见问题(注入、空指针、资源泄漏)反复出现
2. **无量化数据**:组内 review 发现的问题没有归档,无法统计"哪类问题最多、哪个模块问题密度最高",质量改进无数据支撑
3. **修复无闭环**:review 意见提出后,是否修复、如何修复没有跟踪
4. **无定时巡检**:存量代码库缺乏定期自动审查机制
5. **成本不可见**:AI 审查消耗的 token / 大模型调用次数无记录,无法评估 ROI

### 1.2 产品定位

**CodeReviewSystem = AI 代码审查工作台 + 审查数据管理平台**

- **客户端**(桌面应用):研发日常使用,对接本地 Git 仓库和远端 Git 服务,提供提交树、MR/单提交审查、自动修复分支
- **服务端**(管理系统 + API):集中存储审查记录、修复记录、用量数据;提供统计报表;支持定时任务;控制客户端使用授权

### 1.3 目标用户

| 角色 | 使用场景 |
|---|---|
| 研发工程师 | 提交代码前/MR 合入前发起审查,查看意见,决定是否采用自动修复 |
| 研发组长/技术负责人 | 查看组内问题统计,定位高频问题类型和高风险模块 |
| 管理员 | 管理系统配置(服务器、定时任务、LLM 密钥)、数据归档 |

### 1.4 名词定义

| 术语 | 说明 |
|---|---|
| MR | Merge Request(含 GitLab MR / Gitea PR) |
| 审查任务 | 一次针对 MR 或单个 commit 的 AI 审查动作 |
| 自动修复分支 | 系统基于 MR 源分支创建的修复分支(本地),每个问题一个 commit |
| 授权 | 客户端必须能连上服务端才能使用审查功能(离线禁用) |

## 2. 客户端需求(桌面应用)

### 2.1 连接与授权(硬性前提)

- [ ] **REQ-C01 服务端连接配置**:设置页可配置服务端 IP + 端口
- [ ] **REQ-C02 每日进入卡控**:客户端**每日首次启动/进入软件时**执行授权校验(心跳+校验 client token);校验失败/离线 → 当天审查相关功能禁用,界面明确提示;本地 Git 浏览/提交树浏览不受影响
- [ ] **REQ-C03 连接状态**:主界面常驻显示服务端连接状态(在线/离线),离线时审查按钮置灰
- [ ] **REQ-C04 本地缓存 + 推送**:审查产生的记录(review 信息/修复记录/用量)**先写本地缓存**,连接上服务器后自动批量推送到服务端;离线期间数据不丢失,重连后补传

### 2.2 设置页(参考 Codex 的设置中心风格)

**界面风格要求(Codex 参考)**:设置页采用与 Codex 一致的简洁风格——左侧分组导航/分组卡片、开关式配置项、即时生效、深色为主且可切换浅色主题。

- [ ] **REQ-S01 Git 凭据配置**:
  - SSH Key 路径、HTTPS Token(支持 Gitea/GitLab)
  - 凭据本地加密存储(Windows DPAPI)
- [ ] **REQ-S02 远端仓库管理**:维护多个远端仓库条目(名称、Git 服务地址、项目路径、本地克隆目录),支持增删改查
- [ ] **REQ-S03 本地仓库管理**:自动扫描/手动指定本地仓库目录,建立"本地目录 ↔ 远端项目"映射
- [ ] **REQ-S04 LLM 配置**:模型、base_url、API Key(优先复用服务端配置,可覆盖;用于自动修复引擎)
  - 默认值:base_url `https://opencode.ai/zen/go/v1`、模型 `deepseek-v4-flash`
  - 修复模型可单独指定(fixModel)
- [ ] **REQ-S05 审查偏好**(开关式,即时生效):
  - MR 审查完成后是否**自动回填评论**到 Git(默认关,避免打扰)
  - 是否启用"**自动修复分支**"(默认关;开启后审查完成自动基于 MR 原始分支创建修复分支,每个问题一个 commit,仅本地)
  - 默认审查深度(快速/标准/深度)
- [ ] **REQ-S06 服务端配置**:IP、端口、客户端 Token、连接测试按钮、卡控状态显示
- [ ] **REQ-S07 外观设置**(参考 Codex 主题能力):
  - 主题:深色(默认)/ 浅色 / 跟随系统,切换即时生效并持久化
  - 界面字体大小:小/中/大(代码区字号联动)
  - 界面语言:简体中文(默认)/ English(预留)
- [ ] **REQ-S08 设置持久化**:所有设置项存本地 `config.json`,修改即时生效;重启不丢失

### 2.3 主界面 — Git 提交树

- [ ] **REQ-T01 仓库/分支切换**:顶部下拉切换已配置仓库;分支选择器支持"仅当前分支 / 全部分支"两种视图
- [ ] **REQ-T02 提交树可视化**:以树/图形式展示 commit 历史,节点显示:提交信息、作者、时间、SHA 前 7 位
- [ ] **REQ-T03 MR 标记**:属于某个 MR 的提交带 MR 徽标(!N),点击跳转 MR 详情
- [ ] **REQ-T04 提交右键菜单**:
  - 审查此提交(单次 commit 审查)
  - 查看详情(改动文件列表、diff 摘要)
- [ ] **REQ-T05 易用性要求**:
  - 切换仓库/分支响应 < 500ms(本地缓存)
  - 提交树懒加载,万级提交可滚动
  - 操作均有进度反馈和日志

### 2.4 审查与回填

- [ ] **REQ-R01 MR 全自动审查**:对选中的 MR 执行:拉取 MR 分支 → ocr review → 意见展示 → 自动回填评论到 Git 服务(可在设置关闭)
- [ ] **REQ-R02 单 commit 审查**:对任意单个提交执行审查(基于该提交相对父提交的 diff)
- [ ] **REQ-R03 审查结果展示**:意见卡片(文件、行号、严重级别、类别、内容、修复建议),按严重程度分组,支持过滤
- [ ] **REQ-R04 去重**:同一位置(文件+行号)已有 AI 评论不重复回填
- [ ] **REQ-R05 审查记录上报**:每次审查完成,将结果(问题清单、token 用量、耗时)上报服务端

### 2.5 自动修复分支

- [ ] **REQ-F01 开关**:设置中勾选"自动修复"后生效;未勾选时仅出意见
- [ ] **REQ-F02 分支创建**:基于 MR 的**原始源分支**(而非 MR 头)创建本地修复分支,命名 `fix/ai/<mr-id>-<时间戳>`
- [ ] **REQ-F03 逐问题提交**:每个修复的问题对应一个独立 commit,commit message 标注问题编号(如 `fix(ai): #3 修复命令注入风险`)
- [ ] **REQ-F04 本地保留**:修复分支仅存在于本地,不自动推送;由研发 review 后决定是否推送/丢弃
- [ ] **REQ-F05 修复记录上报**:每次自动修复动作(分支名、修复的问题数、commit 列表)上报服务端

### 2.6 页面结构(客户端)

```
┌─────────────────────────────────────────────────┐
│ 顶栏: 仓库▾ | 分支▾(仅当前/全部) | 状态 | 设置 │
├──────────────┬──────────────────────────────────┤
│ 提交树(左)   │ 审查结果(右)                     │
│ • 节点+MR徽标 │ 意见卡片/统计/操作按钮            │
│ 右键菜单     │ [审查此MR] [审查此提交] [回填]     │
└──────────────┴──────────────────────────────────┘
```

## 3. 服务端需求(管理系统)

### 3.1 数据管理

- [ ] **REQ-D01 审查记录存储**:每次审查(来源客户端/定时任务)落库:仓库、MR/commit、问题列表(文件/行号/级别/类别/内容)、模型、token 用量、耗时、状态
- [ ] **REQ-D02 修复记录存储**:自动修复的分支、问题数、commit 列表、最终是否被采用(研发反馈)
- [ ] **REQ-D03 用量记录**:每次 LLM 调用记录:模型、输入/输出 token、请求次数、费用(可配置单价估算)
- [ ] **REQ-D04 数据归档**:支持按时间段导出 CSV/JSON;历史数据保留策略可配置

### 3.2 统计报表(管理系统 Web)

- [ ] **REQ-Q01 总览看板**:今日/本周/本月审查次数、问题总数、按严重级别分布
- [ ] **REQ-Q02 问题分类统计**:按类别(注入/空指针/性能…)、按模块/文件路径聚合的 TOP 榜
- [ ] **REQ-Q03 团队维度**:按提交人/审查人聚合问题数、修复率
- [ ] **REQ-Q04 用量统计**:token 消耗趋势(日/周/月)、模型调用次数、估算费用
- [ ] **REQ-Q05 定时任务报告**:每次定时审查的执行结果、成功/失败、问题摘要

### 3.3 定时任务

- [ ] **REQ-CR01 任务创建**:管理员在管理系统创建定时任务:选择仓库、审查模式(MR 列表/指定分支/全量)、cron 表达式或周期(每日/每周)、目标分支
- [ ] **REQ-CR02 执行与结果**:调度器按时执行,自动拉取远端并审查,结果入库;失败重试(最多 3 次)并记录原因
- [ ] **REQ-CR03 任务管理**:任务列表(启停、编辑、删除、立即执行一次)、执行历史

### 3.4 服务端管理

- [ ] **REQ-M01 管理员认证**:管理员账号登录(初始账号初始化脚本创建)
- [ ] **REQ-M02 LLM 密钥管理**:服务端集中维护 LLM provider 配置(多 provider 可切换),客户端可复用
- [ ] **REQ-M03 授权控制**:配置允许接入的客户端(白名单机器名/固定 token);未授权客户端拒绝连接
- [ ] **REQ-M04 运行监控**:服务端自身健康检查(API /health)、日志查看

## 4. 非功能需求

| 编号 | 需求 |
|---|---|
| NFR-01 | 数据库:PostgreSQL(服务端唯一数据源) |
| NFR-02 | 客户端:Windows 桌面应用(Electron),免安装便携版 |
| NFR-03 | 服务端:Windows/Linux 均可部署(Node.js),管理系统为 Web 界面 |
| NFR-04 | 安全性:API 使用 token 鉴权;凭据本地加密;LLM Key 不回传客户端日志 |
| NFR-05 | 性能:常规查询 P95 < 1s;统计报表支持 10 万级审查记录 |
| NFR-06 | 容错:客户端离线时本地可浏览代码但不可审查;服务端宕机不丢已上报数据(客户端本地缓冲待重传) |
| NFR-07 | 多 Git 服务:同时支持 Gitea 与 GitLab(v4 API) |

## 5. 需求优先级(实施顺序)

| 优先级 | 范围 |
|---|---|
| **P0(必须)** | 客户端:连接授权、设置页、提交树、MR/单提交审查、回填;服务端:审查记录落库、用量记录、基础统计、授权 |
| **P1(重要)** | 自动修复分支;定时任务;问题分类统计;数据导出 |
| **P2(增强)** | 团队维度报表、费用估算、客户端离线缓冲、多语言 |

---

## 6. 验收标准(摘录)

1. 客户端配置服务端地址后,离线状态下审查按钮全部禁用
2. 提交树可切换仓库/分支,MR 提交带徽标,右键可发起单提交审查
3. MR 审查全自动:一键完成 拉取→审查→回填,服务端可见本次记录
4. 开启自动修复后,本地出现 `fix/ai/<mr-id>-*` 分支,每个问题一个 commit,不自动推送
5. 服务端管理页可查看:审查记录明细、问题分类 TOP、token 趋势、定时任务执行历史
6. 定时任务按 cron 触发,失败重试,结果入库可查
7. 每次审查服务端记录 token 用量与模型请求次数
